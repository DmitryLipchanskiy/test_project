# Спецификация

## Что делаем

Одностраничное веб-приложение «каталог товаров + корзина» с промокодами и правилами
доставки. Приложение — подопытный объект: его делает агент наивным прогоном
по короткому описанию, а этот документ служит эталоном, против которого оно проверяется.

## Для кого и зачем

Пользователь документа — тестировщик, который получает приложение как чужое,
без доступа к истории его создания. Проблема, которую документ решает: без записанного
заранее ожидаемого поведения проверка вырождается в «выглядит нормально», а любое
странное поведение можно задним числом объявить задумкой. Здесь ожидаемое зафиксировано
до того, как приложение существует.

Второй адресат — агент-разработчик в наивном прогоне. Он этот файл **не видит**:
ему достаётся отдельное короткое описание, в котором часть решений намеренно
не проговорена. Расхождения между тем, что он решит сам, и тем, что записано здесь, —
основной материал для находок.

## Стек и стенд

- Один `index.html`, vanilla JS, без сборщика и без фреймворков.
- Каталог товаров — отдельный `products.json`, загружается через `fetch`.
- Стенд поднимается локальным сервером: `python3 -m http.server 8765`,
  адрес `http://localhost:8765`. Через `file://` не открывается — Playwright MCP
  блокирует этот протокол.

## Каталог

- 8 позиций. У каждой: идентификатор, название, цена.
- Цены в рублях с копейками. **Минимум одна позиция с дробной ценой** — нужна,
  чтобы проверять округление процентных скидок.
- Конкретные названия и цены задаёт наивный прогон; после него они фиксируются
  как тестовые данные и дальше не меняются.

## Сценарии

1. Пользователь открывает страницу, видит каталог из 8 товаров и пустую корзину.
2. Добавляет товар в корзину — в корзине появляется строка с количеством 1,
   пересчитывается сумма.
3. Добавляет тот же товар ещё раз — количество в **существующей** строке растёт
   до 2, вторая строка не появляется.
4. Меняет количество кнопками «+» и «−». При уменьшении до 0 позиция удаляется
   из корзины. Верхний потолок — 99 штук: кнопка «+» на 99 больше не увеличивает
   количество, ручной ввод 100 и выше обрезается до 99. Значение больше 99
   в корзине — дефект.
5. Вводит промокод, применяет — сумма пересчитывается, видна величина скидки.
6. Набирает сумму выше порога — стоимость доставки меняется по правилам ниже.
7. Перезагружает страницу — состав корзины сохраняется, применённый промокод тоже:
   после перезагрузки скидка остаётся действующей, повторно вводить код не нужно.
8. Удаляет из корзины все товары — видит пустое состояние.

Нештатные:

9. Вводит несуществующий промокод — приложение сообщает об ошибке, сумма не меняется.
10. Вводит существующий промокод в другом регистре или с пробелами по краям —
    код **не** применяется (см. правила ниже).
11. Применяет второй промокод поверх первого — первый заменяется, скидки не складываются.
12. `products.json` недоступен или испорчен — приложение показывает ошибку загрузки,
    а не пустую страницу и не «висит».

## Правила расчёта

Ядро спецификации. Порядок шагов важен.

**Шаг 1. Сумма товаров** — сумма «цена × количество» по всем позициям корзины.

**Шаг 2. Стоимость доставки** — определяется по сумме товаров **до применения
промокода**. Базовая стоимость доставки — 400 ₽.

| Сумма товаров (до скидки) | Доставка |
|---|---|
| меньше 2000 ₽ | 400 ₽ |
| от 2000 ₽ включительно до 3000 ₽ не включая | 300 ₽ (скидка 25%) |
| от 3000 ₽ и выше | 0 ₽ — бесплатно |

Граничные значения: ровно 2000 ₽ → 300 ₽. Ровно 3000 ₽ → бесплатно.
1999,99 ₽ → 400 ₽. 2999,99 ₽ → 300 ₽.

**Шаг 3. Скидка по промокоду** — применяется к сумме товаров. Стоимость доставки
в базу для расчёта скидки **не входит**: 10% по `fresh_start` считаются от суммы
товаров, а не от суммы вместе с доставкой.

| Код | Скидка |
|---|---|
| `fresh_start` | 10% |
| `hotweekend` | 50% |
| `1+1` | 500 ₽ фиксированно |

Коды сравниваются **точно**: регистр значим, пробелы по краям не отбрасываются.
`Fresh_Start`, `FRESH_START`, ` fresh_start ` — невалидные коды, приложение
отвечает ошибкой. Это осознанное решение, а не недосмотр: поведение проверяется
отдельным тестом.

Активным может быть только один код. Применение второго заменяет первый,
скидки не складываются.

**Нижняя граница.** Сумма товаров после скидки не уходит в минус и не обнуляется:
минимум — 1 ₽. Корзина на 300 ₽ с кодом `1+1` (−500 ₽) даёт 1 ₽ за товары.
Доставка считается отдельно и прибавляется к этой единице: 1 + 400 = 401 ₽ итого.

**Шаг 4. Итог** = max(сумма товаров − скидка, 1 ₽) + стоимость доставки.

**Округление** — до копеек, математическое: половина копейки округляется вверх.
10% от 1234,57 ₽ = 123,457 → 123,46 ₽.

## Состояния

| Состояние | Что видит пользователь |
|---|---|
| Пустая корзина (первый заход) | Текст «Корзина пуста». Каталог доступен |
| Есть товары | Список позиций с количеством, сумма товаров, стоимость доставки, итог |
| Промокод применён | Строка со скидкой и величиной, итог пересчитан. Сохраняется в `localStorage` вместе с корзиной и переживает перезагрузку |
| Промокод неверный | Сообщение об ошибке рядом с полем, сумма не изменилась |
| Все товары удалены | «Корзина пуста». Поле промокода очищается, применённая скидка снимается — но код **не сгорает**: после нового добавления товаров его можно ввести снова |
| Каталог не загрузился | Сообщение об ошибке загрузки вместо списка товаров |

## Чего точно не делаем

- Оформление заказа, оплата, платёжные формы.
- Авторизация, регистрация, личный кабинет.
- Бэкенд, база данных, любое серверное хранение. Только `localStorage`.
- Адреса доставки, выбор службы доставки, сроки.
- Каталожные функции: поиск, фильтры, сортировка, пагинация, категории.
- Изображения товаров.
- Адаптив под мобильные ширины и доступность — вне периметра проверки этой работы.
- Сборщики, фреймворки, npm-зависимости в самом приложении.

## Допущения

- **8 позиций в каталоге** — число выбрано агентом, человеком не оспорено. Хватает,
  чтобы набрать сумму выше порога 3000 ₽ и при этом не раздувать тестовые данные.
- **Конкретные цены задаёт наивный прогон.** Иначе пришлось бы диктовать их
  в коротком описании, а чем оно подробнее, тем меньше свободы у агента —
  и тем меньше расхождений найдётся.
- **Промокод `1+1` — фиксированные 500 ₽**, несмотря на название, наводящее
  на «второй товар в подарок». Так решил человек; название сохранено намеренно,
  потому что оно само по себе провоцирует агента на свою трактовку.
- **Порог доставки считается по сумме до скидки** — то есть промокод не может
  «сбить» корзину ниже порога и вернуть платную доставку.
- **Нижняя граница 1 ₽ действует только для непустой корзины.** При пустой корзине
  итог 0 ₽, а не 1 ₽, и промокод не применяется вовсе. В ответе человека это
  не проговорено — уточнение агента, оспорено не было. Решение нетипичное:
  обычно нижней границей ставят 0, поэтому проверять надо именно 1 ₽,
  и «итог 0» на корзине в 300 ₽ с кодом `1+1` — дефект, а не удача.

## Открытые вопросы

Места, где спецификация молчала или допускала два прочтения. Агент задавал вопрос,
а не выбирал трактовку сам — это требование Части II `AGENTS.md`. Список ведётся
накопительно и идёт в сдачу: он показывает, что было решено человеком,
а что могло уехать в молчаливое решение модели.

| # | Что было непонятно | Кто заметил | Решение человека |
|---|---|---|---|
| 1 | Базовая стоимость доставки: заданы пороги и скидка 25%, само число нет | агент | 400 ₽; в зоне 2000–3000 → 300 ₽; от 3000 → 0 ₽ |
| 2 | Скидка больше суммы корзины: итог 0 или минус? | агент | Сумма товаров не ниже 1 ₽, доставка прибавляется сверху |
| 3 | Округление копеек при процентной скидке | агент | До копеек, математическое, половина вверх |
| 4 | Процентная скидка от суммы товаров или от суммы с доставкой | агент | От суммы товаров, доставка не входит в базу |
| 5 | Переживает ли применённый промокод перезагрузку | агент | Да, хранится в `localStorage` вместе с корзиной |
| 6 | Максимум количества: «99, при попытке ввести больше будет 100 и так далее» — если потолок 99, откуда 100 | агент | Формулировка признана ошибочной: 99 — жёсткий потолок везде, ввод выше обрезается |
| 7 | Нижняя граница 1 ₽ на пустой корзине — тоже 1 ₽? | агент | Не проговорено человеком; принято допущение: на пустой корзине итог 0 ₽ |
| 8 | Судьба исходного `README.md` из комплекта после переписывания под сдачу | агент | Остаётся только в истории git (`git show ad277d1:README.md`) |

**Открыто на текущий момент:** ничего. Строки добавляются по ходу работы —
пустой список к концу проекта означал бы, что вопросы не задавались.

## Критерии приёмки

- [ ] Тест-план на 10–12 проверок, минимум треть — негативные или граничные.
      По каждой проверке есть отметка: пройден / провален / заблокирован.
- [ ] Три баг-репорта по формату из `AGENTS.md`, на каждый — доказательство:
      скриншот или лог.
- [ ] Из них одна находка доказана скриншотом, другая — разбором разметки,
      и написано, почему наоборот не вышло бы.
- [ ] Один Playwright-тест, падающий на реальном дефекте. Зелёный тест,
      ничего не проверяющий, критерий не закрывает. Желательно Page Object Model,
      плюс подключённый Playwright MCP.
- [ ] Один баг починен, после фикса прогнан весь чек-лист целиком. Записано,
      что починилось и что сломалось попутно.
- [ ] Список неоднозначностей непустой: места, где `SPEC.md` молчал и агент задал
      вопрос вместо своей трактовки.
- [ ] Список расхождений «агент сказал готово / проверка опровергла» непустой.
      Первая запись уже есть — история с `git init`.
- [ ] Есть хотя бы один зафиксированный случай, где запрет из `AGENTS.md`
      остановил агента от действия.
- [ ] Сравнение наивного тестирования и тестирования по спеке — в цифрах,
      не «стало лучше».
- [ ] Стенд поднимается строго по `README.md`, без дописывания недостающих шагов.
