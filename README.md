# Проверка корзины интернет-магазина

Домашнее задание после занятия 1, **направление QA (задание 4)**.
Тема — корзина интернет-магазина с промокодами и правилами доставки.

**Продукт этой работы — проверка, а не приложение.** Приложение в `app/` сделано
одним промптом без спецификации и правил, руками не правилось (кроме одного
согласованного фикса) и служит подопытным объектом. Сдаётся то, что вокруг него:
[спецификация](SPEC.md), [тест-план](qa/test-plan.md), [баг-репорты](qa/bugs/)
с доказательствами, [автотесты](tests/), [журнал](sessions/) и
[разбор расхождений](qa/discrepancies.md) — где отчёт агента разошёлся с фактом.

Исходный `README.md` из учебного комплекта переписан; он доступен командой
`git show ad277d1:README.md`.

## Как запустить

Нужны **Node.js 18+** ([nodejs.org](https://nodejs.org/en/download)) и
**Python 3** ([python.org](https://www.python.org/downloads/)). Проверить:
`node --version`, `python3 --version`.

**На Windows** часть команд отличается — см. раздел [«Windows»](#windows) внизу.

**0. Склонировать репозиторий:**

```bash
git clone https://github.com/DmitryLipchanskiy/test_project.git
```

Дальше все команды выполняются **из корня репозитория** (`cd test_project`).

**1. Установить зависимости** (одна — `@playwright/test`):

```bash
npm install
```

**2. Скачать браузер для тестов:**

```bash
npx playwright install chromium
```

Если браузер уже скачан, команда завершается молча, без вывода — это нормально,
код возврата `0`. Проверить, что именно установлено:
`npx playwright install --dry-run chromium`.

**3. Поднять стенд:**

```bash
python3 -m http.server 8765
```

**На Windows — `python` вместо `python3`,** иначе команда падает с `exit 9009`.
См. раздел [«Windows»](#windows) внизу.

Команда не завершается — оставьте её в отдельном окне терминала.
Порт 8765 менять нельзя: адрес зафиксирован в тест-плане и в конфигурации тестов.
Если порт занят, посмотрите, кто его держит: `lsof -nP -iTCP:8765 -sTCP:LISTEN`
(на Windows — `Get-NetTCPConnection`, см. раздел [«Windows»](#windows)).

**4. Открыть приложение:**

```
http://localhost:8765/app/index.html
```

При первом заходе видно каталог из 8 товаров и пустую корзину с текстом
«Корзина пуста. Добавьте товары из каталога.», итог 0,00 ₽.
Так это выглядит: [qa/evidence/readme-step4-app-opened.png](qa/evidence/readme-step4-app-opened.png).

**5. Прогнать тесты** (в другом окне терминала, стенд из шага 3 может остаться
запущенным — конфигурация переиспользует его; если стенд не поднят, она поднимет
его сама — на Windows см. раздел [«Windows»](#windows)):

```bash
npx playwright test
```

**Ожидаемый результат — `1 passed, 3 failed`.** Это норма, а не поломка.

Тесты сверяют поведение приложения со `SPEC.md`, а не с кодом. Четыре дефекта
найдены, исправлен по согласованию только один — BUG-03, его тест зелёный.
Три остальных дефекта оставлены в приложении намеренно, и их тесты обязаны
падать: красный тест здесь — зафиксированное расхождение, а не сломанная
проверка. Зелёный прогон всех четырёх означал бы, что тесты списаны
с реализации и ничего не проверяют.

Вывод прогона целиком сохранён в [qa/evidence/playwright-run-02-after-fix.txt](qa/evidence/playwright-run-02-after-fix.txt),
а состояние до фикса — в [playwright-run-01-red.txt](qa/evidence/playwright-run-01-red.txt) (там `4 failed`).

## Windows

Проверено на чистой Windows 11 Pro (PowerShell 5.1), где из инструментов был
только git. Полный отчёт — [qa/evidence/clean-machine-report.md](qa/evidence/clean-machine-report.md).
Содержательно всё воспроизводится: тесты дают те же `1 passed, 3 failed`,
приложение открывается в описанном виде. Отличаются три команды.

**1. `python3` не существует.** Вызов уходит в заглушку Microsoft Store
и завершается кодом `9009`:

```
python3 : Python was not found; run without arguments to install from the Microsoft Store
EXITCODE=9009
```

Работают `python` и `py`. Шаг 3 выглядит так:

```powershell
python -m http.server 8765
```

Автозапуск стенда из `playwright.config.ts` подставляет нужную команду сам —
он выбирает `python` на Windows и `python3` на остальных системах.

**2. `lsof` не существует.** Кто занял порт 8765:

```powershell
Get-NetTCPConnection -LocalPort 8765 -State Listen | Select-Object OwningProcess
```

**3. `curl` в PowerShell — это алиас `Invoke-WebRequest`**, он не понимает
ни `-sI`, ни конвейер в `head`. Нужен явный `curl.exe`:

```powershell
curl.exe -sI http://localhost:8765/app/index.html | Select-Object -First 1
# HTTP/1.0 200 OK
```

Эта подмена не падает громко — легко принять ошибку алиаса за недоступный
стенд и пойти чинить не то.

**Установка рантаймов через winget**, если их нет:

```powershell
winget install --id OpenJS.NodeJS.LTS -e --source winget
winget install --id Python.Python.3.13 -e --source winget
# перезапустить терминал, чтобы подхватился PATH
```

## Сравнение двух прогонов

Сравниваются не две реализации приложения, а **два подхода к его проверке**.
Приложение одно.

| Показатель | Наивное тестирование | Проверка по `SPEC.md` |
|---|---|---|
| Промптов | 1 | тест-план на 13 проверок |
| Проверено | 12 областей | 13 проверок, из них 9 негативных и граничных |
| Найдено дефектов | **0** | **4** |
| Прочих наблюдений | 3 (stale-запись, мёртвый код, доставка до скидки) | 2 неоднозначности спеки |
| Проверок с отметкой «заблокирована» | 0 | 3 |
| Вердикт | «приложение функционально корректно» | 10 пройдено, 3 провалено, 3 заблокировано |

Из четырёх дефектов наивный тестировщик **три проверил поимённо и назвал
корректными**, четвёртый не проверял вовсе:

| Дефект | Что сделал наивный прогон |
|---|---|
| BUG-01 потолок 999 вместо 99 | «Количество — >999→999 — всё верно» |
| BUG-02 промокод нормализуется | «Валидация промокодов — регистр, пробелы — корректно» |
| BUG-03 обнуление суммы товаров | «Ограничен суммой товаров (min), итог не уходит в минус» |
| BUG-04 промокод на пустой корзине | не проверял |

**Вывод: разница не в тщательности, а в наличии эталона.** Наивный прогон
работал добросовестно — поднял стенд, кликал по-настоящему, вызывал внутренние
функции, читал консоль, проверял XSS и битый JSON. Его отчёт подробнее иных
наших разделов. Но ожидаемые значения он выводил из кода, который перед этим
прочитал, — а в такой рамке несовпадение возможно только там, где код
противоречит сам себе. Требование, записанное человеком снаружи, туда не
попадает никогда.

Поэтому нормализация промокода читается как забота о пользователе, потолок 999 —
как разумное ограничение, обнуление суммы — как защита от отрицательных
значений. Все три решения выглядят осмысленными. Дефектами их делает не качество
кода, а то, что в `SPEC.md` записано другое.

## Что не покрыто

Находки независимого аудита ([сессия 7](sessions/session-7.md)), которые приняты, но не закрыты: их
закрытие расширяет объём против плана. Записаны, потому что незаписанная граница
неотличима от недосмотра.

1. **Тест `bug-03` остался бы зелёным и на неверном фиксе** — через условие
   «если скидка больше суммы», которое пропустило бы случай равенства. Граница
   равенства держится на разборе формулы (ЗБ-03), а не на тесте.
2. **Раздел `SPEC.md` «Чего точно не делаем» не проверяется ни одной проверкой.**
   Негативное требование «в каталоге нет поиска и фильтров» проверяется одним
   селектором и поймало бы, если бы наивный прогон дорисовал лишнее.
3. **Испорченный `localStorage` не проверен** — ТП-12 покрывает только битый
   `products.json`. Код устойчив (`loadState` с `try/catch`), но это нигде
   не подтверждено.
4. **Нечисловой и дробный ввод количества** (`2.9` → 2, отрицательное →
   удаление) не зафиксирован даже как наблюдение. Непоследовательность:
   момент применения ввода в список неоднозначностей внесён, а разбор значения —
   нет.
5. **Итог 0 ₽ на пустой корзине не закрыт прямым ассертом**, хотя допущение
   названо в спеке нетипичным.
6. **Пустая корзина на первом заходе** проверяется только косвенно — текст
   «Корзина пуста» ассертится после удаления товара, а не при первой загрузке.

## Заблокированные проверки

Три требования спецификации проверить на текущих данных невозможно. В [тест-плане](qa/test-plan.md)
они помечены `заблокирован` — не `пройден`.

| ID | Требование | Почему нельзя проверить |
|---|---|---|
| ЗБ-01 | Порог доставки ровно на 2000,00 ₽ | Сумма ровно 2000,00 ₽ из каталога не набирается; ближайшие 1999,50 и 2004,00 |
| ЗБ-02 | Округление копеек при процентной скидке | Все цены кратны 50 копейкам → 10% кратно 5 копейкам, 50% — 25 копейкам; дробной копейки не возникает |
| ЗБ-03 | Скидка ровно равна сумме товаров | Нужна корзина ровно на 500,00 ₽ — номинал фиксированной скидки; ближайшие 470,00 и 513,00 |

Достижимость сумм проверена перебором; независимо подтверждена аудитором,
который прогнал собственный subset-sum и получил те же результаты.

**Общий вывод: тестопригодность данных закладывается вместе с данными.**
У всех трёх блокировок одна причина — восемь цен, кратных 50 копейкам, которые
наивный прогон выбрал произвольно, потому что в коротком описании о них ничего
не говорилось. Ни одна не связана с качеством кода. Лечится это тестовым
каталогом с ценами вроде 999,99 и 0,33 — но `app/products.json` менять нельзя,
он часть зафиксированного артефакта. Подменить границу соседней достижимой
точкой и написать «пройден» было бы враньём: ошибку сравнения «больше» вместо
«больше либо равно» ровно на пороге такие точки не ловят.

## Допущения и ограничения

- **Модель наивных прогонов отличается от рабочей.** Приложение и наивное
  тестирование делал Opus 4.8, рабочие сессии шли на Opus 5. Разница между
  прогонами объясняется не только наличием эталона, но и сменой модели;
  разделить вклад этих факторов по имеющимся данным нельзя.
- **Изоляция наивных прогонов неполная.** Папки были чистыми (проверено:
  ни `CLAUDE.md`, ни `AGENTS.md` выше по дереву нет), но скиллы из
  `~/.claude/skills` подключаются в любой сессии независимо от каталога.
- **ЗБ-03 подтверждён разбором формулы, а не тестом.** Разбор проверяет формулу,
  переписанную в тестовый код, и не заметит, если изменить строку в приложении.
  Автотест написать нельзя — см. раздел о заблокированных проверках.
- **Стенд раздаёт наружу весь корень репозитория**, включая `SPEC.md`
  и папку `sessions/`. Для локальной проверки безразлично, но это не то
  поведение, которое годится за пределами localhost.
- **Теоретическая дыра в фиксе BUG-03:** при сумме товаров меньше 1 ₽
  выражение `subtotal - 100` уходит в минус и скидка стала бы наценкой.
  На текущем каталоге недостижимо — минимальная цена 135,00 ₽. Страховка
  `Math.max(0, …)` закрыла бы и это, но выходит за рамки согласованной правки
  в одну строку.
- **Инструкция запуска проверена на macOS и на чистой Windows 11.** На Windows
  найдены три расхождения (`python3`, `lsof`, `curl` как алиас PowerShell) —
  учтены в разделе «Windows» и в конфигурации тестов. Отчёт о прогоне:
  [qa/evidence/clean-machine-report.md](qa/evidence/clean-machine-report.md).
  На Linux инструкция не проверялась; `python3` там штатная команда,
  но утверждать это как проверенный факт нельзя.
- **Исходный шаблон `sessions/session-1.md` потерян** — перезаписан агентом
  до `git init`, в историю не попал. Отмечено в журнале, а не скрыто.

## Как велась работа

**Девять сессий, роли не смешивались.** Разработчик (наивный прогон),
тестировщик (проверка), чинящий (один фикс), аудитор — каждая роль в отдельной
сессии. Наивные прогоны выполнялись в папках вне репозитория: `CLAUDE.md`
читается и из родительских каталогов, поэтому «новой сессии» для изоляции
недостаточно — этого хватило бы, чтобы агент увидел спецификацию.

**Запреты из `AGENTS.md` сработали трижды**, и каждый раз по-разному:

1. Порт 8765 держал процесс от наивного прогона, `curl` при этом отвечал `200`.
   Запрет «порт занят — сообщить, а не выбрать соседний молча» заставил
   разобраться, кто слушает порт. Иначе проверялась бы копия вне репозитория.
2. В тест-план было записано «поднять стенд на другом порту» — нарушение того же
   запрета, написанного мной же. Поймал человек.
3. Правка BUG-03 была очевидна с момента находки, но запрет на починку в роли
   тестировщика удержал от неё. Без этой паузы не появились бы ни красный тест,
   ни разбор случая равенства скидки и суммы — дефект закрылся бы раньше,
   чем стало понятно, что он шире описанного.

**Список расхождений — [qa/discrepancies.md](qa/discrepancies.md).** Тринадцать случаев,
где заявленный результат не совпал с фактическим, плюс шесть смежных. Там же видно,
кто их ловил: в первых сессиях — человек, к концу работы агент начал ловить
себя сам, дважды до того, как ошибка попала в отчёт. Последние два нашёл аудитор.

Центральный вывод этого списка:

> **Из тринадцати случаев одиннадцать — одна и та же механика: подтверждение
> выполнения шага выдавалось за достижение цели.**
>
> Команда вернула ноль — значит сделано. Файл записан — значит правка легла.
> Сервер ответил 200 — значит стенд поднят. Каталог на экране — значит файл
> прочитался. Скрипт вернул JSON — значит данные верны. Во всех случаях
> доказательство было настоящим; неверным был переход от него к выводу.

Практическое следствие вписано в `AGENTS.md` по ходу работы: формулировка
«сделать X» в правилах недостаточна — нужна пара «сделать X» и «доказать выводом
какой именно команды», причём доказательство должно отвечать на вопрос о цели,
а не о шаге.
